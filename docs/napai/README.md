## 3. 評分項目對照

| 評分項目（比重） | 系統提供的證據 | 目前的缺口 |
|---|---|---|
| 任務完成度與穩定性（25%） | 端到端測試 79 項＋閉環測試全數通過；規則模式評測成功率 90.9%；API 失敗自動重試與降級；沒有金鑰也能完成同一流程 | 真實模型下的成功率與延遲尚未量測 |
| 場域成效與使用者驗證（20%） | 畫面內建回饋（讚／倒讚）、線上指標、驗證程序與紀錄表 | **沒有真人數據**，這一項目前拿不出證據 |
| Agentic 技術深度與適切性（20%） | 入口＋能力盤點＋三個 Agent 的分工；有相依的多步驟；依錯誤修正；平行工具；跨回合脈絡；規則計分與語言模型的分工說明 | 真實模型的規劃表現待量測 |
| 安全可控性與治理（15%） | 人工確認、工具白名單、去識別化（實測送出的請求）、同意與撤回、上限、輸出檢核、軌跡、稽核、教師下架、刪除帳號 | 校內對外部 API 的規定未確認；資料自填的真實性靠事後驗證 |
| 創新與擴散價值（10%） | 同一套 Skill ID 串起課程、證照、競賽、教師；結案互評回寫成已驗證的證據；其他學校換掉參考資料即可使用 | 擴散所需的資料整理成本（科目表、教師資料）需說明 |
| 現場展示與答詢（10%） | Demo 劇本、備援路徑、預想問答 | 需彩排 |

## 4. Agentic AI 定義對照

競賽辦法對 Agentic AI 的要求（轉述）：能把任務拆成至少兩個有相依關係的步驟，並具備下列至少兩項。

| 要求 | 本系統 | 驗證 |
|---|---|---|
| 至少兩個有相依關係的步驟 | 能力盤點 → 推薦競賽 → 找互補隊友（用前一步的競賽編號與缺口）→ 找指導老師 → 起草案件（用候選人代號） | `napai_e2e.py` 步驟 2；評測案例 F1、F2、S1、T1、M1 |
| 工具／API 呼叫 | 7 個工具，背後是能力盤點模組與三個 Agent | 步驟 1、2 |
| 依結果或錯誤調整 | 工具回傳錯誤 → 改用另一個工具；API 失敗 → 重試、降級 | 步驟 6、8 |
| 安全機制：人工確認、權限、紀錄、回復、輸出檢核 | 待確認動作、登入者權限、`agent_steps`／`event_logs`、降級為規則模式、輸出檢核 | 步驟 4、7、9、11、12 |

## 6. 待指導老師決定的參數

討論表註明「可修改」的項目，系統都做成管理後台可調的參數；目前的預設值如下。

| 項目 | 目前預設 | 在哪裡改 |
|---|---|---|
| 三階門檻 | 初階 60、中階 70、進階 85（含下界） | 管理後台「等級三階的門檻」 |
| 研究所成績門檻 | 70／80／90 | 同上 |
| 自述證據的計分上限 | 100（不設限）；設 84 即自述最高到中階 | `self_declared_cap` |
| 修課成績是否算已驗證 | 否（顯示為「修課成績」） | `course_grade_verified` |
| 誰來驗證證照與作品集 | 管理員 | 管理後台「待驗證的證據」 |
| 證照對照表的內容與分數 | 36 張，分數為整理時的建議值 | 管理後台／`ref-base.sql` |
| AI 擷取自動生效的信心門檻 | 80% | `llm_auto_approve_pct` |
| 結案證據的相符度門檻 | 成立 3.0、認可原有較高分數 4.0 | `case_evidence_min_match_x10`、`case_confirm_match_x10` |
