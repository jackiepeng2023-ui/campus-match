# Agent 評測資料

測試案例、基準線、指標定義、紀錄與可查核的操作軌跡。所有數字都可以用本頁的指令重現。

| 項目 | 位置 |
|---|---|
| 評測工具 | `backend/tools/agent_eval.py` |
| 測試案例（22 個） | `backend/tools/eval/cases.json` |
| 結果 | `backend/tools/eval/out/REPORT-<label>.md`、`results-<label>.json`、`trace-<label>-F1.json` |
| 治理與流程的端到端測試（79 項） | `backend/tools/napai_e2e.py`（搭配測試替身 `mock_anthropic.py`） |
| 線上指標 | 管理後台「AI 助理評測」、`GET /api/v1/admin/assistant/metrics` |

## 1. 現況

| 模式 | 狀態 | 證據等級 |
|---|---|---|
| 規則模式（基準線） | 已量測，2026-11-11 | 一手：實跑，可重現 |
| LLM 模式（Claude Sonnet 5.5） | **尚未量測**。開發環境沒有 API 金鑰；通訊流程與治理機制已用測試替身驗證 | 待團隊以真實金鑰執行 |

測試替身不是語言模型：它依固定劇本回覆工具呼叫，用來確認系統送出的請求合乎 API 規定、以及遇到各種回應（平行工具、錯誤、拒答、429、5xx、編造的數字）時系統的行為。它的結果**不能**當成模型表現。

## 2. 執行方式

```bash
# 後端以示範資料啟動（APP_SEED_MODE=demo）。每次執行前工具會呼叫 /admin/reset，所以結果可重現；不要對正式資料庫執行。

# 基準線：規則模式（先撤回示範帳號的 AI 同意，跑完恢復）
python3 backend/tools/agent_eval.py --mode rule

# LLM 模式：後端以真實金鑰啟動後執行；標籤自動為 llm
APP_ANTHROPIC_API_KEY=sk-ant-... java -jar backend/target/campus-match-1.0.0.jar
python3 backend/tools/agent_eval.py

# 只跑部分案例、指定要匯出軌跡的案例
python3 backend/tools/agent_eval.py --only F1,A1,G1 --trace A1 --label llm-partial
```

22 個案例約 27 個回合。以 Claude Sonnet 5.5 的公告單價（每百萬 token 輸入 2 美元、輸出 10 美元）粗估，完整規劃類的回合每則約 2 萬個輸入 token，整輪評測的費用預期在 1 美元以內；**實際以報告中的 token 數與帳單為準**（這是依測試替身回合的 token 量所做的推論，不是量測值）。

## 4. 指標定義

| 指標 | 定義 | 資料來源 |
|---|---|---|
| 任務成功率 | 自動判定條件全部成立，且最後一則回覆正常結束（`END_TURN` 或規則模式）的案例 ÷ 全部案例 | `agent_messages`、`agent_steps`、`agent_actions`、`cases` |
| 正確率 | 所有回覆的輸出檢核通過（回覆中的分數、日期、學生代號都能對應到工具結果），且回覆提到的首選競賽與競賽 Agent 的第一名一致的案例 ÷ 全部案例 | `agent_messages.checks`、卡片 |
| 平均／中位／最大延遲 | 每回合從送出到完成的時間 | `agent_messages.duration_ms` |
| 成本 | 輸入、輸出 token × 設定的單價；另列每回合成本 | `agent_messages.input_tokens`／`output_tokens` |
| 工具調用成功率 | 成功的工具呼叫 ÷ 全部工具呼叫；另列各工具的次數、失敗數、平均與最大耗時 | `agent_steps.ok`、`duration_ms` |
| 重試次數 | 模型呼叫因 429／529／5xx 自動重試的次數 | `agent_messages.llm_retries` |
| 人工介入率 | 產生待確認動作的案例 ÷ 全部案例（線上指標為助理回合） | `agent_actions`、`agent_steps` |
| 中止率 | 因工具呼叫輪數上限、拒答、回覆截斷而停止的回合 ÷ 全部回合 | `agent_messages.stop` |
| 降級率 | Claude API 失敗後改用規則模式的回合 ÷ 全部回合 | `agent_messages.stop = FALLBACK` |
| 錯誤分類 | 各停止原因的回合數；模型呼叫錯誤依狀態碼分類 | `agent_messages.stop`、`llm_calls.status` |

系統裡所有會改變資料的動作都需要人確認，所以「人工介入率」衡量的是「有多少任務走到需要人做決定的那一步」，不是「模型做不到、需要人接手」的比例。

## 5. 基準線結果（規則模式，2026-11-11）

資料：50 位虛構示範學生、逢甲公開資料（科目表、教師專長）、28 個競賽。案例 22 個、回合 27 個。原始報告：`backend/tools/eval/out/REPORT-rule.md`。

| 指標 | 數值 |
|---|---|
| 任務成功率 | 90.9%（20／22） |
| 正確率 | 100.0%（22／22） |
| 平均／中位／最大延遲 | 25／17／96 ms（規則模式為毫秒級，每次執行略有不同） |
| 工具調用成功率 | 100.0%（40 次呼叫，失敗 0 次） |
| 模型呼叫／重試 | 0／0 |
| 成本 | 0 |
| 人工介入率 | 18.2%（4 個案例產生待確認動作） |
| 中止率／降級率／錯誤率 | 0%／0%／0% |

沒有通過的兩個案例，原因都是規則模式只做關鍵字比對：

| 案例 | 規則模式的行為 | 期待的行為 |
|---|---|---|
| C6「幫我查一個叫做火星殖民創意大賽的比賽」 | 把它當成一般的競賽推薦，呼叫 `recommend_competitions` | 用名稱搜尋，回報資料庫沒有這個競賽 |
| S2「我想找會 Vue 和 UI/UX 設計的人一起做專題，每週大概 6 小時」 | 句子裡沒有「隊友／組隊」等關鍵字，沒有呼叫任何工具 | 從句子取出需求技能與時數，呼叫 `recommend_teammates` |

這兩個案例是用來量測「語意理解帶來的差距」的；LLM 模式的結果應與這張表並列比較。延遲與成本的差距同樣要列出：規則模式是毫秒級、零成本，LLM 模式每回合需要數次模型呼叫。

## 7. 可查核的操作軌跡

`trace-<label>-F1.json` 是案例 F1（完整規劃）的完整軌跡，由 `GET /assistant/sessions/{id}/trace` 匯出。結構：

| 欄位 | 內容 |
|---|---|
| `messages[]` | 每一則訊息：角色、內容、模式（LLM／RULE）、停止原因、耗時、模型呼叫與重試次數、token、工具呼叫與失敗次數、輸出檢核結果 |
| `messages[].steps[]` | 每一步：順序、Agent、工具名稱、輸入參數、**交給語言模型的輸出**（其他學生為代號）、摘要、耗時、成功與否 |
| `actions[]` | 這個對話產生的待確認動作及其狀態、建立與決定時間 |

基準線軌跡（規則模式）的五個步驟：

| 順序 | Agent | 工具 | 輸入 | 結果摘要 | 耗時 |
|---|---|---|---|---|---|
| 1 | 能力盤點 | `get_my_skill_profile` | — | 9 項技能（進階 7、中階 2；修課成績 8、已驗證 1） | 4 ms |
| 2 | 競賽 Agent | `recommend_competitions` | limit 5 | 可報名 5 筆；最高「AI CUP 2026 秋季賽」55.1 分 | 5 ms |
| 3 | 學生 Agent | `recommend_teammates` | competition_id 2 | 團隊缺口 4 項、候選人 38 位、建議組合 1 人可補齊 | 14 ms |
| 4 | 教師 Agent | `recommend_teachers` | competition_id 2 | 專長相符 103 位，回傳前 3 位 | 18 ms |
| 5 | 待確認動作 | `draft_team_case` | competition_id 2 | 動作 #1：建立組隊案件並邀請 1 位隊友（待確認） | 8 ms |

查核方式：軌跡裡每一步的輸出，都可以用同一位示範學生登入後呼叫對應的 API（`/agents/competitions`、`/agents/teammates`、`/agents/teachers`）重新取得並比對。

## 9. 限制

1. 案例數 22 個，涵蓋主要意圖與治理情境，但不是統計上有代表性的樣本；成功率的信賴區間很寬（22 個案例中差 1 個就是 4.5 個百分點）。
2. 自動判定只看得到「呼叫了哪些工具、有沒有產生動作、數字對不對得上」；回覆好不好懂、建議合不合理，需要人工檢查欄。
3. 示範學生是虛構的，技能分布由程式產生，與真實學生的分布不同。
4. 「正確率」的定義是對內一致性（回覆與工具結果一致），不是推薦本身是否為最佳選擇；後者要靠場域驗證（[`field-validation.md`](field-validation.md)）。
